## Includes 0.1.19, which was not published

The 0.1.19 build stopped before anything was published: the dependency audit found
CVE-2026-114605 in dnspython 2.8.0. There is no `domainlens:0.1.19` image. This release holds
everything in 0.1.19, with dnspython 2.9.0, the release with the fix. Coming from 0.1.18, read
`docs/releases/0.1.19.md` as well: its upgrading section applies to this release too.

## Every package in the image is pinned, with its hashes

`requirements.txt` pinned only the packages DomainLens imports. What those pull in -- Flask's
werkzeug and jinja2, requests' urllib3, idna and certifi, cryptography's cffi -- was whatever was
newest on the day the image was built. An image could therefore hold versions the tests and the
dependency audit never saw, and a package replaced on the index would have been installed
without anyone noticing.

- **`requirements.in`** now lists the direct dependencies, with the reasons for their pins.
- **`requirements.txt`** is the lock made from it with `pip-compile`: all 31 packages, each with
  its SHA-256 hashes. The image installs it with `--require-hashes` and refuses anything that
  does not match.
- **CI** installs the same lock, audits every package in it with pip-audit (transitive ones
  included), and fails when the lock no longer matches `requirements.in`.
- **The image itself is scanned.** The repository scan saw `requirements.txt` only. Before
  anything is published, the built image is now scanned with Trivy as well, including the
  Debian packages of the base image. A HIGH or CRITICAL vulnerability with a fix stops the
  release.
- **Dependabot** proposes updates weekly for the Python packages (lock included), the base image
  and the GitHub Actions. Each one passes the same tests, audit and image scan.

## WHOIS without the text parser

Registration data came from RDAP and, beside it on every lookup, from python-whois: a general
WHOIS text parser that shelled out to the `whois` command with the domain name, and read most
registries' layouts wrong. RDAP and the registries' own port-43 WHOIS (asked directly by
DomainLens itself) give the same data structured, so the parser, its dependency `python-dateutil` and the
`whois` command are gone from the image.

- RDAP answers first. When it gives no answer -- no RDAP at the registry, or no reply -- the
  registry's own WHOIS is asked. Before, port 43 was asked only when a registry had no RDAP at
  all.
- The scan's WHOIS tab no longer shows a second, "WHOIS (port 43)" table under the RDAP one.
  An older scan still shows it, as it was stored.
- "Domain expires soon", its evidence and the takedown dossier read the expiry date, the
  registrar and the abuse address from the registration data. The expiry warning no longer
  fails on a date without a time zone, which is what registries give.

### Upgrading

Nothing to do for the image. To run DomainLens outside Docker on Linux or macOS, install with
`pip install --require-hashes -r requirements.txt`. On Windows use `pip install -r
requirements.in`: the lock is made for the Linux image. After changing `requirements.in`,
regenerate the lock with the command at the top of that file.
