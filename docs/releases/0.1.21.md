## The tools no longer stall while lists and CVE data are written

Writes to the database were committed one row at a time, and the app's write lock was held all
the while. Storing the CVE data of a sync held it for close to a minute (PHP alone for 28
seconds), and a threat list for the mail analysis (100,000 addresses, twice a day) for minutes.
Every other write waited, and every lookup in **Tools** writes something -- its audit entry, a
cached answer -- so a lookup could take 18 seconds instead of a hundredth of one.

These writes are now one transaction each. On a copy of a production database:

| | before | now |
|---|---|---|
| CVE data of all seven products written | 44.6 s | 0.4 s |
| A threat list of 107,000 addresses written | about 3 minutes | 2 s |
| An audit entry during a CVE sync | up to 18.5 s | 0.01 s |
| **Tools → Versions**, the CVE overview | 0.7 s | 0.004 s |

A list or CVE update that fails half-way now leaves what was there before. Until now the old
list was already deleted, so a failure in between left the mail analysis or the IP check
without that list until the next successful download.

**Tools → Versions** now keeps its CVE overview until a sync stores new data, instead of
reading all 30,000 ranges on every visit.

## A published version is not built again

The image was built and pushed on every push to main, also when `VERSION` stayed the same. A
merged Dependabot update would therefore have replaced `domainlens:0.1.20` with an image holding
other packages than the 0.1.20 that was released, and a rollback to that tag would land
elsewhere. A push to main now publishes only when its version has no release or tag yet; any
other push runs the tests and says in the run that nothing was built.

Dependabot's pull requests are therefore not merged one by one: their updates come in with the
next version, as here.
