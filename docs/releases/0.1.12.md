## Outlook messages, attachments read safely, and the Spamhaus PBL read for what it is

### Outlook .msg files in the mail analysis

Tools → Mail analysis refused an Outlook `.msg` file ("it should start with header lines"),
though it is what Outlook saves. It now reads one: the headers the receiving server added (when
Outlook kept them), the body as HTML, as plain text, or from the compressed RTF Outlook sometimes
keeps instead, and every attachment.

A `.msg` file does not keep the body as it was sent, so a DKIM signature over it cannot be
verified: DKIM reads *not measured*, never *fails*, with the receiving system's own verdict
(Authentication-Results) shown where the message carries it. Everything else -- the Received
chain, SPF, DMARC, the sending server, links and attachments -- is read as from an `.eml` file.
A sent item or a draft has no received headers; the page says what that leaves out.

### Attachments read for what they do, safely

Attachments were judged by their name, and later PDFs by their insides, in the same process as
everything else. Every attachment -- and any file chosen on its own on the same page -- is now
read for what it does when opened, the static half of what a sandbox such as Joe Sandbox does:

- the real type against the name (a program or web page named `.pdf`), right-to-left marks and
  double extensions;
- PDF: links, forms, JavaScript and the calls known exploits use, actions on opening, a
  program to start, files inside;
- Office: macros read from their VBA source and whether they run on opening, Excel 4.0 macro
  sheets, templates fetched from the internet, DDE, linked and packed objects, passwords;
- RTF: the Equation Editor object (CVE-2017-11882) and other embedded objects;
- archives: their contents read in turn, programs among them, passwords, ZIP bombs;
- HTML: login forms, HTML smuggling, redirects;
- programs, scripts, shortcuts and disk images whatever their name.

Nothing is opened or run. The files are read in a separate process with no environment and no
network, with limits on memory, CPU, files and processes (Linux) and on time (everywhere): a
file that trips a parser stops only that process and is reported as *not measured*. Each file's
SHA-256 is asked of MalwareBazaar (abuse.ch key) and VirusTotal (when switched on for the mail
analysis) -- the hash only, never the file. The content of a file or message never leaves the
server: uploading a document to such a service would make it visible to its other users. The
page says so beside the hash links, and tests fail if anything but a hash is ever sent.

### Quotes escaped on every page

Three pages escaped `<`, `>` and `&` but not quotes, and their output also went into attribute
values. A `"` in a link or file name from an analysed message could end an attribute and add
one; the Content-Security-Policy kept scripts out, a style could still get in. Every page now
escapes both quotes.

### The Spamhaus PBL is no longer a listing

A home or office address answered by Spamhaus ZEN with a PBL code only (127.0.0.10 or .11)
showed *Listed on 1 blocklist(s)* in red, and a monitor would have raised a critical event. The
PBL lists ranges that should not send mail directly -- nearly every home and office connection
is on it; it says nothing about reputation. It now reads *end-user range (PBL)*, with what that
means; an SBL or XBL code beside it still makes it a listing. The mail analysis gives a medium
finding when a message was sent straight from such an address, since receivers that use
Spamhaus may refuse it. A monitor whose last scan counted only the PBL may report the listing as
resolved once.

### Upgrading

New dependency `olefile` (in the image). For known-malware lookups set the abuse.ch Auth-Key (already used for ThreatFox and URLhaus), or switch VirusTotal on under Settings → Mail analysis.
