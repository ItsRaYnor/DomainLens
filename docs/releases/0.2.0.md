## Signing in no longer sends you to another site

`/login?next=…` sent a signed-in user wherever `next` pointed, including
`https://evil.example/` and `//evil.example/` (which a browser reads as another host). A link
to the real DomainLens sign-in page could therefore land the user on a copy of it, right after
they had signed in for real. The same held for local sign-in, MFA, OAuth and SAML.

`next` is now kept only when it is a path on DomainLens itself. Anything else goes to the
start page.

## The session cookie is marked Secure over HTTPS

The session cookie was sent without the `Secure` flag unless `SESSION_COOKIE_SECURE` was set.
On an installation served over HTTPS, a browser would still send it over a plain `http://`
link to the same host, where anyone on the network path can read it.

It is now marked `Secure` whenever the request arrived over HTTPS. Behind a reverse proxy
that terminates TLS, that needs `DOMAINLENS_TRUSTED_PROXY_HOPS` set, as before for client
addresses. An installation served over plain HTTP works as it did.

## Sign-in attempts are limited per address

Failed sign-ins locked the account, but nothing limited one address: it could try one common
password against every account, each staying under its own lockout, or lock any account by
failing on purpose. Sign-in and MFA attempts are now limited to 20 per 5 minutes per client
address; the page says so when the limit is reached.

The in-memory rate limiter also forgets addresses whose requests have expired. Before, every
address that ever made a request stayed in memory until a restart.

## Uploads have a size limit

A request body of any size was accepted and written to `/tmp` (memory, in the hardened
container) before a handler looked at it. Requests over 60 MB are now refused with a 413; the
largest upload DomainLens takes, an InsightVM export, stays capped at 50 MB.

## The HTTP checks do not fetch from your own network either

0.1.22 stopped the JavaScript scan, the security checks and the active scan from fetching
internal addresses. The header check, the HTTPS-redirect check, the MTA-STS policy fetch, the
infrastructure check, the default-credentials test and the software version check still did.
They now refuse a connection that reaches an address on the server's own network, including
after a redirect or a DNS answer that changes between lookups.

A refused check says so: "points to an address on this server's own network, which DomainLens
does not fetch. Not measured." It is not reported as a missing redirect or missing headers,
and an HTTPS redirect that could not be verified is no longer listed as a high finding.

To scan internal hosts on purpose, set `DOMAINLENS_ALLOW_PRIVATE_TARGETS=true`. That lifts the
restriction for every check, including those 0.1.22 restricted.

## A scan that no longer exists says so

Returning to a scan the server no longer knows (finished more than a day ago, or lost) made
the progress bar disappear without a word. It now says the scan is no longer available.

## Upgrading

Nothing to do, unless you scan hosts that resolve to private addresses (an intranet, a lab,
a staging environment on 10.x or 192.168.x). Those checks now read "Not measured"; set
`DOMAINLENS_ALLOW_PRIVATE_TARGETS=true` to scan them as before. That is why this is 0.2.0
rather than 0.1.23.
