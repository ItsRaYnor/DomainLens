## The example secret key from the documentation no longer signs anything

The compose files and the README show `DOMAINLENS_SECRET_KEY` as `change-me-openssl-rand-hex-32`
(and, in a few places, `long-random-string`). An installation started from them unchanged
signed its session cookies and its SCIM access tokens with a value anyone can read on GitHub:
with it, a session cookie naming an administrator, or a SCIM token that provisions a new
account, can be made without ever signing in.

Those two values are now refused for signing. Sessions and SCIM tokens are signed with the
random secret DomainLens keeps in its database instead, and the log says why at start-up.

Stored credentials (integration passwords, API keys) are still encrypted with the example
value, because a different key could not read the ones already stored. **Settings** now says
so in plain words: "Not protected", with what to do about it.

## Requests from other sites are refused

Any web page a DomainLens user had open could make their browser post to DomainLens -- add a
monitor, change a setting, revoke a token, start a scan -- in their name. The session cookie's
SameSite setting stopped most of that in current browsers, but not from a sibling subdomain
(`blog.example.com` posting to `lens.example.com`), not in older browsers, and not at all on an
installation with login switched off: there is no cookie to withhold, and the request simply
went through.

Every POST, PUT, PATCH and DELETE now has to come from a DomainLens page. The browser reports
where a request came from (`Sec-Fetch-Site`, or else `Origin` or `Referer`), and anything from
another site is refused with a 403 and a line in the log. Signing in from another site is
refused too, so nobody can sign a user in to an account of their choosing.

Left as they were:

- **API tokens and SCIM.** A request that carries an `Authorization` header is not checked: a
  browser never adds one to a request from another site by itself.
- **SAML sign-in.** The identity provider posts the assertion from its own site by design; the
  signature on the assertion protects it, as before.
- **Scripts and `curl`** that send none of these headers.

## The scanner no longer fetches from your own network

The JavaScript scan fetches the scripts and source maps a page links, and follows its
redirects; the web checks and the active scan follow redirects too. A scanned site that linked
a script on `http://10.0.0.1/` or redirected to `http://169.254.169.254/` (a cloud provider's
metadata service) had DomainLens fetch it from inside your network.

These requests now check the address each connection actually reached, after DNS, and refuse
anything that is not a public address. That also covers a name that resolves to a public
address when it is checked and to an internal one when it is fetched.

The check of what counts as internal is one definition now, instead of four copies that all
missed `0.0.0.0`, carrier-grade NAT (`100.64.0.0/10`), multicast and IPv4 written as IPv6
(`::ffff:127.0.0.1`), and that looked only at a name's first address.

The main scan of a domain you enter is unchanged: an internal domain can still be scanned.

## Measurements that failed are no longer shown as clean

Four probes returned, when they got no answer, the same value as a clean result:

- **TLS compression** showed "Disabled (safe)" when the handshake did not happen.
- **CORS** showed `(none)` and **Allowed methods** showed nothing, as if measured.
- The **reverse DNS** API answered "no PTR records" when the lookup timed out.

They now say **Not measured** (the API answers 502 with a reason).

## OVHcloud's DKIM selectors are checked

A domain on OVHcloud's hosted mail signs with the selectors `ovhmo-selector-1` and
`ovhmo-selector-2`. DomainLens did not try them and reported such a domain as having no DKIM.
Both are now in the built-in list.

That alone would not have reached most installations. Saving any scan setting stored the whole
selector list as it was at that moment, and from then on that copy replaced the built-in list,
so a selector added in a later release was never tried there. The built-in list is now always
checked, and the selectors under **Settings → Scan** are checked in addition to it.

## A scan survives a restart of DomainLens

A scan that was running when DomainLens restarted disappeared: the page polling it lost track
of it without a word, and whether it had run could not be told. It is now reported as
interrupted, with the advice to start it again. A scan that finished is still answered after a
restart, with its result from the scan history.

## Operations

- **Containers run read-only.** The compose files now start DomainLens with a read-only file
  system (except `/data` and a scratch `/tmp`), without the Linux capabilities it does not
  need, and unable to gain new privileges. Scans, backups, PGP key generation and the file
  sandbox were tested under these limits.
- **Structured logs.** `DOMAINLENS_LOG_FORMAT=json` writes one JSON object per line, traceback
  included, for a log collector. Every request carries an id, in the `X-Request-ID` response
  header and on each log line it caused; an id set by a proxy in front is kept.
- **Schema version.** The database records which schema it carries, and every schema change
  from now on is a numbered step applied exactly once. `/health` shows it (for an admin) next
  to the version the code expects -- the two to compare after restoring a backup.
- **Signed images.** Each published image is signed by the workflow that built it. How to
  verify one: [Docker and updates](../DOCKER_AND_UPDATES.md#verifying-an-image).
- **Built on Windows.** An image built from a Windows checkout failed to start ("no such file
  or directory") because the start script had Windows line endings. The repository and the
  Dockerfile now both keep it in Unix form.

### Upgrading

Nothing to do in most cases.

- If `DOMAINLENS_SECRET_KEY` is still one of the example values above, everyone is signed out
  once. Generate your own (`openssl rand -hex 32`), set it, and enter the credentials under
  **Settings** again: those stored now cannot be read with a new key.
- If DomainLens runs behind a reverse proxy that replaces the `Host` header and the public URL
  is not set, a browser without `Sec-Fetch-Site` support may get a 403 on saving. Set
  `DOMAINLENS_PUBLIC_URL` (or **Settings → General → Public URL**) to the address users open.
- A selector you removed from the list under **Settings → Scan** because it was built in is
  checked again; it costs one DNS query per scan.
- If you use your own copy of a compose file, the hardening above is in the files in this
  repository; copy the `read_only`, `tmpfs`, `cap_drop`, `cap_add` and `security_opt` lines
  across to get it.
