Check a domain

Read a domain's /.well-known/security.txt and follow its Encryption: field to check the PGP key a researcher would actually be told to use.

Three outcomes are kept apart: the key was fetched and read, it could not be reached (ours to admit, not the site's fault), or there is no Encryption: field at all — which is allowed, since the field is optional in RFC 9116.

Validate a security.txt

Paste a file to check it before you publish it. Nothing is fetched and nothing is stored — which is the point: you can check a draft.

Validate a PGP key

Paste an armoured key to see whether it parses, what algorithm it uses, which identities it carries and when it expires. The key is read in a throwaway keyring and never imported or kept.

Paste the public half. A private key is reported rather than refused, because publishing the wrong half is the mistake worth catching here — but do not paste one you still rely on.

Generate a keypair

For a domain you are setting up. Neither half is stored — both are shown once and forgotten, so this is a tool, not a configuration step.

A passphrase encrypts the private key file itself, so the downloaded .asc is useless to anyone who cannot supply it. It is used for this one generation and never stored — if you lose it the key is gone, because there is nothing here that could recover it.

To publish a key for this installation — where the public half is kept and served at /.well-known/pgp-key.asc — use Settings → Responsible disclosure.
